# Стандарты тестирования

## Обязательный TDD

При изменении поведения сначала написать или дополнить тест, запустить его
и убедиться, что он падает по ожидаемой причине. Затем реализовать поведение,
проверить прохождение тестов и выполнить необходимый рефакторинг при проходящих
тестах. Ошибка окружения или компиляции сама по себе не подтверждает отсутствие
требуемого поведения.

## Уровни проверки

- Бизнес-поведение сервисов проверять unit-тестами с моками зависимостей.
- Репозитории проверять интеграционными тестами с тестовой БД.
- HTTP-контракты проверять e2e-тестами. Все endpoints должны быть покрыты.
- Для каждого endpoint проверять успешный сценарий и применимые отказы:
  невалидные данные, отсутствие доступа, отсутствие сущности и бизнес-конфликты.
  Набор сценариев определяется контрактом и требованиями.
- Простые методы сервисов можно не тестировать отдельно, если они не вызываются
  напрямую из контроллера. Методы с бизнес-логикой тестировать независимо
  от места вызова.

## Содержание тестов

- Тесты отражают бизнес-правила и требования, сформулированные в задаче или
  документации. Проверки запросов репозитория отражают требуемый результат
  работы с данными.
- При исправлении бага дополнить подходящий существующий тест или создать
  новый. Отдельный новый тест на каждый баг не обязателен.
- Применимые проверки выбирать по изменению и актуальным scripts в
  `package.json`. В отчёте указывать выполненные проверки и их результат;
  для невыполненных — причину.
