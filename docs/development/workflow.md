# Выполнение задач и ревью

## Подготовка задач

Подготовку выполнять последовательно:

1. Сформулировать продуктовую задачу: описать проблему, ожидаемый результат,
   сценарии, требования, ограничения и критерии приёмки. Название должно отражать
   ожидаемую возможность или результат.
2. Обсудить техническую реализацию на основе продуктовой задачи: рассмотреть
   варианты, зависимости и ограничения, согласовать подход и зафиксировать
   принятые решения.
3. После обсуждения и согласования подхода сформировать технические задачи:
   для каждой описать конкретное изменение, область реализации, зависимости
   и проверки. Название должно отражать конкретное техническое изменение.

Технические задачи являются дочерними по отношению к продуктовой задаче.
В каждой указывать ссылку на родительскую задачу и требования, которые она
покрывает. Продуктовая задача задаёт ожидаемый результат, а технические задачи
описывают согласованный способ его достижения. Завершение технических задач
должно сопровождаться проверкой критериев приёмки продуктовой задачи.

## Нумерация задач

- Каждой новой задаче присваивать уникальный возрастающий номер: `001`, `002`,
  `003` и далее. Использовать минимум три цифры с ведущими нулями.
- Следующий номер выбирать как максимальный из ранее присвоенных номеров плюс
  один. Номера завершённых или отменённых задач сохранять и не использовать повторно.
- Файлы задач хранить в `docs/tasks/` с именем `<номер>-<краткое-описание>.md`,
  например `001-fix-some-issue.md`. Описание писать на английском в `kebab-case`.
- В заголовке документа указывать тот же номер задачи.
- Заголовок pull request (MR) должен иметь формат `<номер>-<краткое-описание>`,
  например `001-fix-some-issue`. Номер должен совпадать с номером задачи;
  это номер задачи проекта, а не автоматически назначаемый GitHub номер PR.

## Ветки задач

- Для каждой новой задачи, включая дочернюю техническую, создавать отдельную
  ветку от актуального `main` с именем `<номер>-<краткое-описание>`.
- В ветке задачи реализовывать только эту задачу. Каждую дочернюю задачу
  выполнять отдельно в собственной ветке, а результат передавать на ревью
  отдельным PR с её номером.
- Родительская задача объединяет требования и критерии приёмки; реализация
  её дочерних задач распределяется по их собственным веткам и PR.

## Выполнение

1. Изучить затронутую реализацию, тесты, применимые инструкции и требования задачи.
2. Определить ожидаемое поведение и критерии приёмки. Существенную неоднозначность
   уточнить; рутинные детали реализации решать самостоятельно.
3. Выполнить изменение по [стандартам разработки](standards.md) и
   [обязательному TDD](testing.md).
4. Выполнить применимые проверки и проверить итоговый diff.
5. Обновить затронутые контракты и документацию.

## Передача на ревью

- Для каждой задачи открывать отдельный pull request из её ветки для ревью
  владельцем проекта.
- В PR описывать результат, выполненные проверки и оставшиеся ограничения.
- Замечания исправлять в той же ветке. Повторное ревью и слияние выполняет
  владелец проекта.
- [Задача автоматического исправления замечаний](../tasks/001-automate-pr-review-fixes.md)
  отменена. Исправление замечаний запускает владелец проекта вручную.

## Состояния готовности

- Готово к ревью: выполнены критерии приёмки, пройдены применимые проверки,
  обновлена затронутая документация, проверен diff и открыт PR.
- Завершено: изменения приняты и слиты владельцем проекта.
- Если окружение, доступы или проверки блокируют передачу на ревью, явно
  сообщить, что выполнено, что осталось и в чём причина блокировки.
