# Стандарты разработки

Этот документ фиксирует согласованные требования. Выбор технологии в стандарте
не означает, что она уже установлена или настроена в проекте.

## Модули и бизнес-логика

- Организовывать модули по предметным областям.
- Предоставлять явный публичный интерфейс модуля. Другие модули используют
  публичные сервисы, без доступа к внутренним репозиториям и деталям реализации.
- Начинать с контроллеров и сервисов NestJS. Независимые бизнес-объекты выделять
  по мере усложнения логики; отдельные слои и интерфейсы вводить по необходимости.
- Контроллер отвечает за HTTP-взаимодействие, сервис — за бизнес-логику.
- В рамках задачи менять соседние модули только для связи модулей друг с другом.
  Улучшения кода выносить в отдельные задачи.

## Типизация

- Сохранять строгую проверку TypeScript (`strict`).
- Для непроверенных внешних данных использовать `unknown` и проверять их перед
  использованием.
- Применение `any`, приведений типов и подавлений ошибок требует конкретного
  обоснования, доступного при ревью изменения.
- Автоматически проверяемые требования закреплять в конфигурации TypeScript,
  Oxlint и Prettier. При расхождении конфигурации со стандартом явно отмечать это.

## Репозитории и транзакции

- Доступ к сущностям БД выполнять через репозитории своего предметного модуля.
- Репозитории инкапсулируют запросы и особенности хранения. Сервисы используют
  методы репозиториев и не обращаются к БД напрямую.
- Методы возвращают данные сущностей и скрывают ORM: сервисам не передаются
  query builder, ORM-условия поиска и другие механизмы построения запросов.
- Сложные операции записи внутри одного модуля можно выполнять в транзакционном
  методе репозитория с названием по смыслу операции, например `createWithOwner`.
- Бизнес-решения остаются в сервисе; репозиторий обеспечивает атомарность и
  ограничения хранения данных. Перенос транзакции не должен переносить в
  репозиторий бизнес-логику.
- Проверки, требующие защиты от конкурентных изменений, выполнять внутри
  транзакции; их смысл определяется бизнес-правилами.
- Транзакционные границы между модулями проектировать под конкретный сценарий.
  Универсальную абстракцию заранее не вводить.

## HTTP API

- Для проверки входных данных использовать `class-validator`.
- Структуру входных данных проверять на HTTP-границе, бизнес-условия — в сервисе.
- Явно описывать контракты запросов и ответов отдельно от сущностей БД.
  Возвращаемые поля выбирать явно, чтобы изменение хранения не меняло API случайно.
- Модуль определяет собственные типы ошибок для ожидаемых отказов и выбрасывает
  их внутри модуля. Бизнес-логика и репозитории не зависят от HTTP-статусов.
- Контроллер обрабатывает известные ошибки модуля и преобразует их в
  HTTP-исключения. Неизвестные ошибки передаются стандартному обработчику NestJS;
  внутренние подробности не включаются в ответ клиенту.
- Формат ответов пока стандартный для NestJS. Собственная обязательная обёртка
  успешных ответов или единый пользовательский формат ошибок не утверждены.
- Каждый endpoint документировать в Swagger/OpenAPI: входные данные, успешный
  ответ, ожидаемые ошибки и требования авторизации.
- Обновление HTTP-контракта и его документации входит в ту же задачу.

## Конфигурация

- Читать переменные окружения через единый механизм конфигурации.
- Проверять обязательные значения при запуске. При некорректной конфигурации
  завершать приложение с понятной ошибкой.
- Описывать необходимые переменные в `.env.example` без секретов.

## Изменения БД

- Изменять схему через версионируемые миграции.
- Для изменений существующих данных описывать в задаче перенос данных и
  восстановление при сбое.
- ORM и инструменты миграций выбирать при подключении БД.

## Зависимости и отложенные решения

- Небольшие вспомогательные зависимости можно добавлять самостоятельно,
  обосновывая выбор в PR.
- Технологии, влияющие на архитектуру, включая ORM и авторизацию, согласовывать
  до реализации. При выборе возможностей NestJS читать [справку](nestjs.md).
- Стандарты внешних HTTP API определить при первой интеграции.
- Правила работы с кешем пока не определены.
- Логирование, хранилище и просмотр логов выбрать в рамках
  [отдельной задачи](../tasks/002-configure-logging.md).
