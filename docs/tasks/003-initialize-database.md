## Проблема и ожидаемый результат

В проекте нет подключения к базе данных, команд управления схемой и окружения
для проверки работы с PostgreSQL. Подготовить основу для последующей разработки
предметных модулей на TypeORM: конфигурацию подключения, миграции, запуск в Docker
и изолированные интеграционные тесты.

Разработчик должен иметь возможность запустить приложение на хосте или в Docker,
создать и применить миграцию, посмотреть её статус и выполнить откат. Docker
должен поддерживать разработку с hot reload и запуск собранного приложения.

## Согласованная реализация

### Подключение и конфигурация

- Установить совместимые с NestJS 12 версии `@nestjs/typeorm`, `typeorm`, `pg`
  и `@nestjs/config`; проверить актуальную документацию и совместимость пакетов.
- Создать `DatabaseModule` и отдельный CLI `DataSource` с общей конфигурацией
  подключения и обнаружения сущностей.
- Производственные сущности и миграции хранить внутри `src`, чтобы они попадали
  в `dist`. Поддержать запуск из TypeScript и собранного JavaScript, загружая
  только файлы текущего формата без дублирования.
- Отключить `synchronize` и автоматическое применение миграций при старте.
- Создать локальный `.env`, исключённый из Git, и версионируемый `.env.example`
  с демонстрационными значениями без реальных секретов.
- Использовать `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` и `PORT`.
  Проверять обязательные значения и диапазоны портов до подключения. Ошибки
  конфигурации должны быть понятными и не раскрывать пароль.
- Переменные процесса имеют приоритет над `.env`. На хосте использовать
  `localhost`, внутри Compose переопределять адрес БД именем сервиса.

### Docker и хранение данных

- Добавить многостадийный Dockerfile с целями `development`, `build`
  и `production`. Production содержит собранное приложение и зависимости
  времени исполнения.
- Основной `compose.yaml` запускает PostgreSQL и production-приложение.
  Явно подключаемый `compose.dev.yaml` переключает приложение на `start:dev`,
  монтирует исходники и хранит `node_modules` отдельно.
- Использовать PostgreSQL 18 с закреплённым тегом версии, постоянным named volume
  и `pg_isready` healthcheck. Приложение ожидает готовности БД через
  `depends_on` с условием `service_healthy`.
- Добавить `.dockerignore`; секреты, тесты и локальные артефакты не должны
  попадать в production-образ.

### Миграции

- Добавить npm-команды `migration:create`, `migration:generate`,
  `migration:run`, `migration:revert` и `migration:show`.
- Для `run`, `revert` и `show` добавить варианты с суффиксом `:prod`,
  использующие `dist` без `ts-node`.
- Миграции применять отдельной явной командой. Документировать передачу имени
  и пути миграции, запуск команд на хосте и внутри контейнеров.
- Начальная производственная конфигурация не содержит предметных таблиц
  и фиктивных миграций.

### Изолированная проверка БД

- Добавить отдельный `compose.test.yaml` с изолированным PostgreSQL
  и временным хранилищем, не связанным с рабочим volume.
- Тестовую миграцию хранить исключительно в `test`, вне production-сборки
  и путей обнаружения производственных миграций.
- Тестовая миграция создаёт `database_probe` с автоматически генерируемым
  целочисленным `id` и `created_at` типа `timestamptz` с текущим временем
  по умолчанию. HTTP API для этой таблицы не добавлять.
- Проверить подключение, применение миграции, запись и чтение строки,
  статус миграций, повторное применение без изменений и откат.
- Удалять таблицу при завершении теста. В `finally` выполнять дополнительную
  очистку на случай ошибки проверки или отката и закрывать соединения.
  Проверить отсутствие таблицы после очистки.
- Тестовый DataSource явно использует тестовую БД и тестовую миграцию.
  Предусмотреть защиту от запуска этих проверок с конфигурацией рабочей БД.
- Проверить запуск CLI из `dist` на БД без производственных миграций
  и отсутствие тестовых таблиц, сущностей и миграций в production-сборке.
- Сохранить существующий e2e-сценарий `GET /`, подключив его к тестовой БД
  и обеспечив корректное закрытие соединений.

## Критерии приёмки

- Приложение подключается к PostgreSQL на хосте и в обоих Docker-режимах.
- Некорректная конфигурация отклоняется до подключения с понятной ошибкой.
- Все перечисленные команды миграций работают; собранные команды не требуют
  зависимостей разработки. Схема не изменяется автоматически при старте.
- Данные рабочей БД сохраняются после перезапуска контейнера.
- Hot reload подхватывает изменения исходников в режиме разработки.
- Интеграционные тесты используют отдельную БД. Таблица `database_probe`
  существует только во время теста и удаляется после его завершения,
  включая завершение с ошибкой проверки.
- В production-образе и производственном наборе миграций нет тестовой таблицы
  и кода её создания.
- Пройдены применимые unit-, интеграционные и e2e-тесты, сборка, lint,
  проверка форматирования, конфигураций Compose и обоих Docker-режимов.
- Документированы подготовка env, запуск обоих режимов, миграции, тесты
  и сохранность данных. Указано, что изменение реквизитов в env
  не перенастраивает уже созданный PostgreSQL volume.

## Порядок выполнения и ограничения

- Перед реализацией оформить дочерние технические задачи по согласованным
  направлениям выше со ссылкой на эту задачу, зависимостями и проверками.
- Соблюдать обязательный TDD: сначала падающие тесты конфигурации
  и интеграционного поведения, затем реализация.
- Работать в отдельной ветке, сохранить пользовательские изменения,
  проверить итоговый diff и подготовить PR по правилам репозитория.
- Автоматические seed-данные, админка БД и инфраструктура production-развёртывания
  не входят в задачу.
- На момент подготовки задачи Docker daemon недоступен. Для контейнерных
  проверок требуется работающий Docker; до выполнения проверки не считать
  пройденными.
